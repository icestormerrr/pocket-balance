# Архитектура

Приложение построено вокруг технических слоёв:

```
UI → adapter → service → repository
```

Зависимости направлены только вправо. Обратные импорты запрещены.

## Слои

### UI

UI отвечает за отображение, действия пользователя и композицию экранов. В UI нет бизнес-правил, прямых обращений к хранилищу и вызовов repository.

Подслои UI:

- `app/` — точка входа, провайдеры, роутер, общий layout и глобальные стили.
- `pages/` — экраны маршрутов. Страница собирает виджеты и entity UI, управляет параметрами маршрута и локальным UI-состоянием.
- `widgets/` — самостоятельные блоки интерфейса, используемые страницами: формы, drawer, сложные пользовательские действия.
- `entities/*/ui/` — небольшие UI-части конкретной предметной области.
- `shared/ui/` — универсальные визуальные компоненты без знания предметной области.

UI вызывает только adapter-хуки.

### Adapter

`entities/*/adapter/` связывает UI с прикладной логикой.

- Адаптеры чтения вызывают service и возвращают данные и состояние загрузки.
- Адаптеры мутаций вызывают service и обновляют связанное состояние данных.
- Adapter может преобразовать формат данных для UI, но не содержит бизнес-правила.
- Adapter зависит от UI-инфраструктуры и service; service от adapter не зависит.

Примеры: `useTransactions`, `useCreateTransaction`, `useCashflowReport`.

### Service

`entities/*/service/` — слой application business rules. Каждый публичный метод service реализует один сценарий приложения: «создать транзакцию», «выполнить перевод», «получить отчёт».

Сценарий (use case):

1. Принимает входную модель сценария, а не данные UI или транспорта.
2. Проверяет правила, необходимые именно для этого сценария.
3. Запрашивает и изменяет данные через интерфейсы repository и других service.
4. Возвращает выходную модель сценария или прикладную ошибку.

Service управляет последовательностью шагов сценария, но не содержит детали его окружения. Например, `createTransfer` проверяет допустимость перевода и создаёт две связанные транзакции; repository решает, как они будут сохранены, а UI — как показать результат.

Внутренний код service зависит только от моделей и абстракций (`I*Repository`, `I*Service`). Конкретные реализации передаются снаружи. Поэтому один use case можно вызвать из страницы, импорта или фоновой задачи без изменения его правил.

### Repository

`entities/*/repository/` отвечает за сохранение и получение данных.

- Реализует интерфейс `I*Repository`.
- Преобразует данные в формат хранилища и обратно.
- Применяет простые фильтры хранения.
- Не содержит бизнес-валидацию и UI-логику.

Замена источника данных должна затронуть repository, а не UI или service.
